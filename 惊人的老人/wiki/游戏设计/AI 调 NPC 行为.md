# AI 调 NPC 行为

脚本化 NPC 的问题是**玩家能背出它的行为**；强化学习 NPC 的问题是**训练完策略就固定了**。本篇记录一种折中：让大模型在运行时只挑「战术标签」，不碰底层动作策略。

> 两篇 arXiv 预印本，均未同行评审，`confidence: low`。实验数据为作者自报，且只在自研的 Unity 原型里验证。

## 问题

战斗 NPC 有两条常见路线，各有明确天花板：

| 路线 | 天花板 |
|---|---|
| 有限状态机 / 行为树 | 玩家遇到过一次就能预判、利用它 |
| 强化学习（PPO 等） | 训练结束后策略固定，无法针对特定对手中途换打法 |

论文里反复引用的一个对照：OpenAI Five 和 AlphaStar 达到专家级水平，但高层策略是硬编码的，**没有「不重训就中途换策略」的机制**。

想要「运行时自适应」，直觉是让大模型直接输出动作。但这行不通——本地推理跟不上每帧控制。

## 方案

### 做法：慢规划 + 快执行

把两个系统按**时间尺度**分开，而不是合并成一个网络：

- **慢层**：本地 7B 大模型每 5 秒读一次游戏状态（结构化 JSON），输出一个战术标签（0–3 之间的单个数字）
- **快层**：5 个 NPC 共享一个已训练好的 PPO 策略，把战术标签当作观察向量里的一个条件输入，继续执行逐帧动作

关键设计：战术标签**在训练阶段就被随机采样并写进奖励塑形**，这样策略网络才知道「标签 0 和标签 1 分别意味着什么空间行为」。如果只在运行时才引入标签，策略不会理它。

来源：[[raw/2026-11-03_arxiv_2609.02931_llm-guided-reinforcement-learning-for-adaptive-npc-behavior.md]]

### 另一种思路：把世界状态变成可校验对象

Orchestrated Reality 指出，当今 LLM 驱动的游戏世界**撑不住持久化状态**：叙事用自由散文断言「谁在哪、刚发生了什么、现在什么是真的」，但没有任何经过校验的表示，因此全自主游戏引擎不可行。

它提出的架构选择是：让一个单例编排 agent（类比桌游 GM）持有**规范化的世界对象**——状态是一棵 JSON 实体树，动作分解为「离散意图种类 + 结构化参数」，转移内核走 Plan-Diff-Validate-Apply 流水线，只提交经过 schema 校验、内容哈希的 JSON 增量。

来源：[[raw/2026-11-03_arxiv_2606.16014_orchestrated-reality-from-role-play-to-living-playable-game.md]]

## 可行性卡

| 落地形态 | 依赖 | 成本量级 | 已验证范围 | 等级 |
|---|---|---|---|---|
| LLM 战术标签 + 共享 PPO 策略 | Unity ML-Agents（PPO）、本地 Mistral 7B + Ollama、文件 JSON 桥接 | 中（需训练 RL 策略 + 部署本地模型；CPU 推理 5–30 秒/次） | 1 个自研 Unity 战斗原型，5 个 NPC，600 局，3 类脚本对手 | **B** |
| 规范化 JSON 世界状态 + PDVA 流水线 | 需自建编排 agent、schema 校验、状态哈希 | 高（论文自述为 work in progress） | 形式化模型 + 1 个单回合示例 + 15 个来自真实部署的说明性事件 | **C** |

**关键量化结果**（LLM 战术标签那篇）：

- 对**会中途换战术**的 Balanced 对手：胜率从 **11% → 24%**（翻倍以上），且对局显著变长
- 对 Evasive 对手：胜率更高、击杀更快，但对局时长未满足严格假设定义
- 对 Aggressive 对手：大模型近乎恒定地选择包围，**适得其反**
- 分析 **2,430 次**战术选择：**83.8%** 选了 Surround，且与对手类型无关——作者结论是「在这个模型规模上，零样本策略区分能力有限」
- 统计方法：Mann-Whitney U 检验（因为 time-to-defeat 有 120 秒上限、不服从正态分布）

## 权衡

| 做法 | 优势 | 代价 |
|---|---|---|
| LLM 只挑战术标签 | 不用重训策略就能有多个行为模式；本地 7B 不外传游戏状态 | CPU 上 5–30 秒/次响应，只能做粗粒度 5 秒轮询；无效响应只能保留旧标签 |
| 大模型直接输出动作 | 理论上限高 | 本地推理跟不上每帧控制，论文明确放弃这条路 |
| 规范化 JSON 世界状态 | 状态可校验、可哈希、可回放 | 工程量最大，且论文自己说是进行中的工作 |

**这份资料没有给出的**：不同模型规模（7B 以上）的效果曲线、真实玩家对战时的体验、以及把标签从 4 个扩到更多是否还成立。

## 示例

Unity 6.3.3 LTS 环境，5 个 NPC 通过 ML-Agents 参数共享共用一个 PPO 策略（作者明确说这不构成正式 MARL——没有集中式 critic、没有联合价值函数、没有显式 agent 间通信，协调靠共享终局奖励）。

一个具体回合：战斗到 30 秒时，bot HP 78%、NPC 平均 HP 52%、3 个 NPC 在 6 单位内；LLM sidecar 判断对手「健康、机动、回避交战」，返回标签 0（Surround），5 个 NPC 同时更新条件输入并重新包抄；10 秒后 bot HP 41% 且退向墙角，LLM 切到标签 1（Aggressive）压上。对照组（无 LLM）全程固定同一行为，没有中途转向的机制。

Orchestrated Reality 那边则是形式化：状态 = JSON 实体树，动作 = `a=(k, x_k)`（离散意图 + 结构化参数），agent 只看到状态的叙事投影 `o=O(s)`。

## 变体与待验证

- **标签数量**：本例是 4 个标签。更多标签是否需要更多训练，文中未提
- **模型规模**：83.8% 的 Surround 偏好被作者归因于「这个模型规模」。换更大模型能否区分对手，文中列为开放问题
- **轮询间隔**：5 秒是 CPU 推理延迟下的折中。GPU 部署能否缩短，未测
- **玩家侧体验**：600 局全是对脚本对手，无真人参与

## 反论与数据缺口

- **最关键的反向证据来自实验自身**：83.8% 的策略选择是同一个标签，说明所谓「自适应」在很大程度上是固定偏好。对 Aggressive 对手反而变差，是明确的失败条件
- **只对「会中途换战术」的对手有效**：Balanced 对手胜率翻倍，但这是三类脚本对手里的一类。不能推广成「对玩家更有效」
- **对照设计有混杂**：基线用 `comboA_v01` 模型、实验组用 `comboB_v02` 模型，两个不同的策略权重。作者声称「唯一自变量是 LLM 引导」，但模型文件不同，这一点在文中未进一步说明
- **Orchestrated Reality 是 work in progress**：摘要明确说「we report work in progress on a framework」，给的是形式化模型和示例，不是跑通的系统。把它列为 C 而不是 B，依据在此
- **两篇都无真人验证**：没有玩家觉得 NPC「更聪明」或「更好玩」的证据
- **无公开代码**：两篇都未给仓库地址，复现需要自行搭 Unity + ML-Agents + Ollama 管线

## 开放问题

- 7B 模型的策略区分天花板具体在哪？换 70B 或更强的模型，83.8% 这个数字会降到多少？
- 5 秒的战术粒度，玩家能感知到吗？还是只体现在统计胜率上？
- 如果对手不是脚本 bot 而是真人，中途换战术的频率和模式都不同，结论还成立吗？
