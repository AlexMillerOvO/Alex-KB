# 物理碰撞检测

物理引擎负责让物体「表现得像真的」：受重力下落、碰撞反弹、摩擦减速。以 Unity 底层的 PhysX 为例，它**不是逐帧连续检测**，而是每隔固定时间（默认 0.02 秒）做一次「快照式」的离散碰撞检测。

> 单一二手来源（百科词条），`confidence: low`。参数与 API 名称未回查官方文档。

## 为什么值得知道

**离散检测的代价是「两帧之间可能跨过障碍」。** 物体够快、墙够薄，上一帧还在墙前、下一帧已在墙后，中间那片空间从没被采样过——这就是穿墙。

引擎给的兜底是**连续碰撞检测（CCD）**：把这一帧的运动轨迹当成一条线段去求交，代价是更耗性能。所以实践中的形态是「绝大多数物体用离散，少数高速物体开 CCD」。

理解这套机制的价值不在实现，而在**定位**：

- 子弹穿人、角色掉出地图、掉落物穿过地板——这些经典 bug 的第一嫌疑人是检测模式
- 但不是所有都是。判定盒（hitbox）与射线检测属于另一套系统，混着查会跑偏

## 示例

- **Unity（2005 至今）**：把 Rigidbody 的 Collision Detection 由 Discrete 改为 Continuous Dynamic，可防止高速物体穿透
- **《任天堂明星大乱斗》**：靠帧间插值与判定盒设计规避这类问题

## 反论与缺口

- **0.02 秒是默认值，不是常数。** 它是固定时间步长（fixed timestep），可以调；调小更精确但更贵。词条把默认值写成了机制本身。
- **「子弹穿人」多数不是 CCD 问题。** 射击游戏普遍用射线检测（hitscan）或独立判定盒，根本不过物理引擎。把这个 bug 归到离散碰撞上，是归因错位。
- **大乱斗的例子与 PhysX 不是同一类问题。** 格斗游戏普遍自研帧同步判定，谈「插值规避穿透」和物理引擎的 CCD 是两套语境，并排放会误导读者以为可以照搬。
- **CCD 的开销量级没给。** 「更耗性能」是定性说法，缺具体量级，无法用来做预算决策。
- **未验证**：新版 PhysX 与 Unity 物理后端在该参数上的默认值是否仍为 0.02 秒。

## 与其他知识的关联

- [[对象池]] — 同属「用固定结构换性能稳定性」：一个固定实例，一个固定采样步长
- [[ECS 与 DOTS]] — 大批刚体同时参与碰撞时，数据布局对物理查询成本的影响会被放大
- [[旷野之息的化学引擎]] — 物理与规则系统的交汇：那边关心「物体之间能发生什么」，这边关心「怎么检测到发生了」
- [[有限状态机]] — 角色撞墙后的行为切换通常由状态机承接，碰撞只是触发器

## 开放问题

- 帧同步游戏里，物理确定性与碰撞检测该怎么取舍？
