# 小目标拆解

把「玩家想达成的大目标」和「他现在真要做的下一步」之间的落差，写成**一句玩家自己的话**——「我还差 20 个粉末就能精炼」——再这句话配一个系统载体、一个即时反馈、一条复用场景和一条风险。这就是「小目标设计方法库」的核心结构。

一个塔防改版项目把 65 条这样的句子编号（A 完成感 8 条 / B 成长感 11 条 / C 收集感 8 条 / D 效率感 8 条 / E 稀缺感 9 条 / F 惊喜感 8 条 / G 证明感 5 条 / H 归属与习惯 8 条），其他设计文档直接引用编号，不必重复描述机制。

> 单一来源：该项目内部设计文档（`raw/2026-11-11_小目标设计方法库.md`），未公开发布、无第三方验证，`confidence: medium`。编号、数值与配置字段属于该项目；可迁移的只有**结构**。

## 一条小目标的四段结构

| 段 | 写什么 | 判断它成不成立 |
|---|---|---|
| 玩家心里那句话 | 第一人称的「我还差 X 就能 Y」 | 写不出这句话，说明这一步只有功能，没有动机 |
| 设计方法 | 一个短名（差量可视化、阶梯、锁价、保底…） | 同一个方法名必须能挂到多个系统，否则它只是个功能描述 |
| 实现载体 | 项目里真实存在的章节、配置表字段或界面 | 载体对不上 = 现在还没有，应登记为缺口，而不是继续写方法 |
| 即时反馈 | 玩家做完这一步，屏幕上立刻变了什么 | 只写「数值变了」不算，要写清哪一屏哪个元素变了 |

另有三列是施工参数：**消耗**（这一步花什么资源）、**复用场景**（这个方法还能用在哪）、**风险 / 红线**（它怎样会做坏）。

这四段的价值在顺序：先有那句话，再去要载体。反过来（先有系统，再给它编一个动机）产出的就是一份功能清单，说服不了任何人。

## 65 条背后的七个动作族

本文按功能归并，原文按 A~H 需求分类——同一批方法，两种切法。归并后只剩七类动作，这是可迁移的部分：

| 动作族 | 做什么 | 典型形态 |
|---|---|---|
| 差量可视 | 把「还差多少」变成可读的数字 | 材料数变红、进度条、MAX 标记、缺件高亮 |
| 阶梯 | 给同一件东西排队列 | 等级、品质档位、稀有度颜色、档位进度 |
| 集合 | 把「凑齐」做成可见的格子 | 图鉴、槽位、套装、部件清单 |
| 一次性里程碑 | 只发生一次的大事 | 首通奖励、封顶解锁、新单位登场 |
| 减摩擦 | 减少点击与等待 | 批量执行、自动整理、双向跳转、免成本拆装、二次筛选 |
| 递增成本 | 让每一次重复更贵 | 局内涨价、锁定加价、体力上限 |
| 随机 + 保底 | 意外与确定性配成对 | 加权池、随机词条、随机槽位、软/硬保底 + 概率公示 |

这七个族不是并列的好设计，而是**必须互相配对**才成立的东西：只有随机没有保底是赌；只有阶梯没有材料来源是空转；只有差量没有获取路径是焦虑。

## 组合范式：方法要成链，不要成表

来源文档给了 5 条链。具体编号属于该项目，链的形状可迁移：

1. **随机 → 可见区间 → 材料来源 → 取舍 → 加价**：随机玩法必须给出可见的改善区间和材料产出，否则是纯赌。
2. **叙事 → 角色 → 时限 → 里程碑**：最强的单点动机链，也最容易做坏——把「失去感」放在教程期是明确的流失风险。
3. **空位 → 差量 → 获取途径 → 一键带路**：玩家从「看见空」到「能补上」只走一次跳转，中间任何一次手动找入口都会吃掉动机。
4. **每日签到 → 活跃任务 → 每日免费 → 保底兑现**：让「来了有确定回报」和「再抽一点有保底」同时成立。
5. **单方法撑一条线**：把几条养成线并成一个总评分，让面板自己会说话，不需要加新系统。

可迁移的判断是：**一条链里必须同时有「看得见」和「够得着」。** 只有看得见（进度条、图鉴百分比）是焦虑；只有够得着（邮件直接发材料）是无感。

## 查重：反向索引

正着查（需求 → 方法）是做设计，反着查（系统 → 用了哪些方法）是做查重。两个系统撞同一套方法，玩家就会觉得「又是这一套」。

来源文档的反向索引里，装备线一个系统挂了 **21 条**方法（成长、收集、效率、稀缺、惊喜全占）。这提示查重的单位不是单个方法，而是**方法组合的指纹**：重复一条方法没关系，重复一整串「随机 + 加价 + 凑齐」就会被感知成同一套。

## 慎用清单才是这套库的主体

65 条里，来源文档专门列出 6 条「可以，但必须配保险」：

| 方法形态 | 必须配的保险 |
|---|---|
| 多次独立随机 | 配保底，或给「次数上限 + 保底档」 |
| 限时窗口 | 配错过补偿，且不放在教程期 |
| 随机槽位 | 配非随机获得路径，否则变成纯运气墙 |
| 失败返还 | 返还比例低于通关奖励，否则玩家主动送死刷奖励 |
| 批量执行 | 中途可停 + 显示累计花费 |
| 低档合成 | 一键合成，否则库存管理成本过高 |

结论比方法本身更硬：**「慎用」不等于「不用」，等于「必须成对出现」。** 一份只有方法名、没有配对保险的设计表，等于把所有风险项都留到了上线后。

来源文档另有 7 条自定付费红线（不卖成品装备与词条结果、不卖关卡进度、不做强制插屏、广告奖励不进长期战力、无 PVP 数值付费、抽卡概率必须公示、不允许不付费无法通关）。它们对齐的是该项目「皮肤 + 广告 + 抽卡」的商业模式，**换模式要重定，不能照搬**。

## 为什么值得知道

**一、它把「玩家想要什么」落到「这一屏显示什么」。** 停在需求层做不出东西；停在功能层说不清为什么做。中间缺的就是「小目标」这一格。

**二、缺口能直接看出来。** 载体对不上就是缺口。来源文档按这个办法列了 8 项（成就系统、图鉴完成度、换装属性对比、新英雄试用场、赛季任务树、每日任务条目、难度自选、历史最佳记录），每一项都是「方法想要、系统没有」。这比写一份「建议新增系统」的提案克制得多，也更可用。

**三、能查重，且成本低。** 编号化是文档工作，不是开发工作；收益是两个团队不会在同一个需求上来回加功能。

## 反论与缺口

- **没有效果验证。** 65 条全部通过「载体可查」，但一条都没通过「玩家真的因此留下」。这套库检查的是**可追溯性**，不是**有效性**；它证明每条方法都能指到一处实现，不证明那处实现有用。
- **65 条里没有优先级。** 原文不给收益排序、不给实现成本、不给「哪条最关键」。而实际做产品最先要答的恰恰是这三个问题，这套库答不了。
- **独立方法数少于编号数。** 原文风险列自己标出至少四组同源（领主复利 / 刻度自证、战斗数据 / 战斗自证、章节进度 / 章节全清、随机槽位 / 随机成长），这些是同一机制的两个用途，被拆成两条编号。编号数 65 ≠ 方法数 65。
- **库是「先有系统、后有方法」。** 载体列全部指向已有章节与配置表，说明这套库是对既有系统的编号与归类，不是从需求出发推导新系统。把它当设计起点，会得到一堆「已有功能的重新命名」。
- **即时反馈列不可验收。** 「材料数变红」「锁图标亮起」是 UI 描述，没有一条给出玩家是否注意到的验证方式；反馈强度、出现时机、打断成本全部未定。
- **7 条红线是单项目口径。** 对齐的是该项目自己的变现模型。买断制或纯外观付费的项目套用会得出错误结论。
- **「21 条方法挂一个系统」可能是反面信号。** 原文把它当查重线索，但换成另一种读法：一个系统要 21 条方法才成立，说明它承担了太多动机，玩家在该系统内的每一次停留都被要求「感到点什么」。
- **未验证**：同屏小目标的数量上限（原文只在弹窗一处给了「一次会话不超 2 个」的经验值，且没有来源）；小目标密度与节奏的关系；65 条里删掉一半会损失什么。

## 开放问题

- 一条小目标的「即时反馈」该多强？越强的反馈，重复几十次后衰减越快，而这个衰减曲线没有数据。
- 65 条方法里删掉一半，损失的是什么？原文没有做减法实验。
- 这套结构用在买断制（无抽卡、无体力、无日常）上还能剩几条？
- 反向索引能不能自动化：从配置表反查每个系统用了哪些方法，而不是手工维护一张表？
