# ECS 与 DOTS

ECS（Entity-Component-System）是一种**按数据组织代码**而不是按对象组织代码的架构。Entity 只是一个 ID，Component 只存数据，System 统一遍历处理同类数据。

> 单一二手来源（百科词条），`confidence: low`。性能数据来自 Unity 官方口径，未独立复现。

## 是什么

对比传统面向对象：

| | 传统 OOP | ECS |
|---|---|---|
| 行为归属 | 枪自己知道怎么开火 | 开火系统批量处理所有带武器的东西 |
| 数据布局 | 分散在对象实例里 | 同类型数据连续存放 |
| 扩展方式 | 继承 / 组合 | 加 Component，加 System |

Unity 的 DOTS 技术栈 = ECS + Job System + Burst 编译器，是这套思路的官方实现。

## 为什么值得知道

**它解决的是「海量同质对象」的性能天花板。**

- 数据连续存放 → CPU 缓存命中率上升
- 可多核并行
- 零 GC 分配

Unity 官方给出的实测对比（词条转述）：

| 方案 | 1 万个对象 |
|---|---|
| MonoBehaviour | 约 22 FPS，每帧 GC 分配 320KB |
| DOTS + Burst | 单帧 0.8ms，GC 归零 |

词条的结论是「10 万个对象反而比原来 1 万个还快」。割草、弹幕、RTS 这类「满屏敌人」的玩法，天花板往往就卡在传统架构上。

## 落地方式：混合架构

实际项目很少全量迁移。常见做法是**性能热点用 ECS，UI 和剧情仍用 MonoBehaviour**。

Unity 官方技术文章与《幻面之旅》（团结引擎项目）都把 ECS 列为高密度战斗的优化方向——数百敌人同屏时先靠 SRP Batcher 扛渲染，再逐步把敌人逻辑迁入 ECS 批量处理。

## 反论与缺口

- **性能数据是厂商自证。** 22 FPS vs 0.8ms 这组数字来自 Unity 官方，属于卖点材料，不是第三方基准测试。数字口径也不一致（一边是 FPS，一边是单帧毫秒），不能直接相减比较。
- **「10 万比 1 万还快」这句在逻辑上可疑。** 不同架构、不同对象规模下的对比，缺少同架构横向数据支撑。
- **未讨论迁移成本。** 从 MonoBehaviour 迁到 ECS 的重构代价、团队学习曲线、调试难度，词条完全没有提及——而这通常是决定能不能落地的关键。
- **未验证**：SRP Batcher 的具体收益、团结引擎项目的实际数据。
