# 协程与异步加载

协程（Coroutine）是 Unity 里「把一件事分摊到多帧做完」的写法：函数返回 `IEnumerator`，用 `yield return` 在某处暂停，引擎每帧在 `Update` 之后调用一次 `MoveNext()` 把它推进一步。

**它不是多线程**——代码全跑在主线程，只是把「等待」交给帧循环驱动。

> 单一二手来源（百科词条），`confidence: low`。API 细节以 Unity 文档为准。

## 异步加载为什么必须存在

同步 `LoadScene` 会卡住整帧：音效断、画面冻，手游上还可能触发系统的无响应检测。异步加载把资源流式读进来，同一帧里游戏仍在渲染，所以挂得上一个真正的加载界面。

## 两个必须知道的坑

| 坑 | 现象 | 处理 |
|---|---|---|
| `allowSceneActivation = false` 时 progress 停在 0.9 | 进度条卡在 90% 不动 | 显示时除以 0.9 归一化；剩下 0.1 是「激活场景」 |
| 加载器脚本住在旧场景里 | 旧场景一卸载，协程被杀 | 加载器常驻（`DontDestroyOnLoad` 或独立 bootstrap 场景） |

另一条工程限制：协程不能返回值，只能靠回调或成员变量取结果；每次启动还会生成一个迭代器堆对象——高频场景（每帧轮询）要留意 GC。

## 例子

多数 Unity 手游的启动流程就是这个结构：一个只放加载 UI 的 Bootstrap 场景 → 协程异步加载主场景并推进度条 → 到 0.9 等玩家点「继续」→ 放开 `allowSceneActivation`。

需要返回值、超时或取消时（Addressables、网络请求），业界普遍改用 UniTask 或 Unity 6 的 Awaitable——**协程缺的正是这三样能力**。

## 反论与缺口

- **「协程不是多线程」经常被误解。** 它在主线程跑，重计算放进去照样卡帧；真正的并行要走 Job System 或线程池。
- **0.9 的归一化是权宜之计**，不同版本与加载方式下 progress 的分段可能不同，硬编码 0.9 迟早踩坑。
- **UniTask / Awaitable 不是纯粹升级**：迁移会改变异常传播、取消语义与生命周期绑定方式，老项目整体替换的成本常被低估。
- **未验证**：不同 Unity 版本下 `progress` 的实际分段行为。
