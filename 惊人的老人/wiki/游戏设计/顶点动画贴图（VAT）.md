# 顶点动画贴图（VAT）

VAT（Vertex Animation Texture）把一段动画「烤」成图片：横轴是顶点编号、纵轴是帧号，像素的 RGB 通道直接存该顶点在该帧的位置。运行时着色器按「顶点 UV → 帧 UV」采样一次，就把顶点搬到烘焙好的坐标上——**整套骨骼蒙皮在运行时被删除。**

> 单一二手来源（百科词条），`confidence: low`。16 位精度、包围盒归一化等实现细节未回查原始技术文档。

## 是什么

传统骨骼动画每一帧都要在 CPU 上做蒙皮计算：遍历骨骼层级、算矩阵、逐顶点混合权重。VAT 把这笔账换了个地方——

| 环节 | 骨骼动画 | VAT |
|---|---|---|
| 动画数据 | 骨骼关键帧 + 蒙皮权重 | 一张（或几张）浮点纹理 |
| 运行时开销 | 逐角色 CPU 蒙皮 | 一次纹理采样 |
| 能否实时改动作 | 能（IK、布娃娃、程序化） | 不能，动画被写死 |
| 内存 | 骨骼 + 权重，随角色数不增 | 顶点数 × 帧数，与实例数无关 |

最后一行是它真正的价值点：**内存与实例数解耦。** 同一段动画，1 个观众和 3000 个观众占的动画内存一样，只是多画 3000 次——这正好是 GPU Instancing 擅长的形态。

## 为什么值得知道

**它解决的不是「动画好不好」，是「同屏能不能放得下」。** 骨骼动画是 CPU 逐角色算的，几十个就开始吃紧；VAT 把开销压成一次采样，配上 instancing，几千个动画体在预算内。

**代价是三条硬约束，都在立项时就要认：**

1. **动画不可交互**：不能做 IK、不能布娃娃、不能按玩家操作实时改姿势。选它等于承认这批角色的动画「只需播放，不需响应」
2. **精度不够会抖**：顶点位置要归一化到包围盒、通常用 16 位浮点存；位数或归一化范围没算好，顶点会在帧间跳
3. **内存 = 顶点数 × 帧数**：得塞进单张纹理（或有限的几张），帧率越高、顶点越密，越容易超预算

这三条合起来给了一个很清楚的适用边界：**观众、人群、植被、道具这类「数量大、行为单薄」的动画体适合 VAT；主角、Boss、需要被打断和混合的动作不适合。**

## 举个例子

《Tennis Clash》（Wildlife Studios，2019）的观众席：几千个挥手、欢呼的观众，每个都是独立的 Mesh，不是蒙皮网格——这是生成方给出的典型场景。

> 词条的来源列表还提到 Unity 官方博客里《后院棒球》用 VAT 处理草地的案例，但正文没有展开，本文不据此判断它的适用范围。

## 对照方案：骨骼动画与蒙皮

3D 角色的主流做法不是把顶点烤进纹理，而是**绑骨骼、让蒙皮跟着骨骼变形**：每个顶点按权重分配给骨骼（膝盖处 60% 跟大腿、40% 跟小腿），关节弯曲才平滑。

| 维度 | 骨骼蒙皮 | VAT |
|---|---|---|
| 存储 | 只存骨骼关键帧，体积极小 | 存整段顶点位置，体积随帧数线性涨 |
| 灵活性 | 可混合、可打断、可程序化调整 | 播放即固定，难打断 |
| 计算 | GPU 蒙皮，支持大量实例 | 采样即可，几乎零计算 |
| 典型用途 | 主角、可交互角色 | 大量同屏小怪、植被、特效 |

**选型的判断点不是「哪个更先进」，而是「这个角色需不需要被打断」。** 权重刷得不好会出现「糖果纸」塌陷——肘弯瘪下去，这是蒙皮最常见的质量事故。

## 反论与缺口

- **「几千个不掉帧」没有量级。** 缺机型、GPU、顶点数与帧数的实际预算，无法换算成自己的项目能不能用。
- **替代方案被隐去了。** 词条把选择写成「CPU 蒙皮 vs VAT」，但实际还有 GPU 蒙皮（骨骼矩阵塞进纹理/uniform，在显存里算）。GPU 蒙皮同样避开 CPU 开销，却保留了可交互性——**VAT 真正不可替代的场景比词条描述的要窄。**
- **精度问题只有定性描述。** 「16 位浮点 + 包围盒归一化」是常见做法，但顶点抖动在什么量级下可见、怎么测，词条没给。
- **内存估算缺算例。** 「顶点数 × 帧数塞进单张纹理」听起来可控，实际一个 5000 顶点、60 帧的动画就是 30 万像素级的数据，词条没有给出边界。
- **案例是幸存者样本。** 两个案例都出自引擎/中间件厂商的技术宣传材料，天然偏向成功案例。
- **未验证**：Tennis Clash 观众的实际实例数与实现方式。

## 与其他知识的关联

- [[LOD]] — 同一类取舍的两个维度：LOD 按距离降几何精度，VAT 按「动画要不要响应」降动画能力；都是拿「精度/自由度」换吞吐
- [[ECS 与 DOTS]] — 海量同质对象的两条腿：ECS 解决「数据怎么摆」，VAT 解决「动画怎么算」；只换一个，另一个仍是瓶颈
- [[对象池]] — 同属「为同屏大量实例服务」的工程手段：对象池省的是创建与销毁，VAT 省的是每帧求值
- [[顶点色]] — 同一个思路的轻量版：都把数据塞进顶点属性（或纹理）让 GPU 直接取，一个存颜色，一个存位置；差别在数据量与更新频率

## 开放问题

- 一个「观众级」角色在 1080p / 60 帧下的 VAT 内存上限是多少？
- GPU 蒙皮已经能解决 CPU 瓶颈，VAT 还剩下哪些非它不可的场景？
- 动画不能响应操作，对「看起来像活的」这件事的损失有多大？有没有可测的观感指标？
